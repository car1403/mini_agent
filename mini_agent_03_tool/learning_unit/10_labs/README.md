# 03 Tool Use 실습

기본 예제 `00`~`08`을 학습한 뒤 아래 실전 Lab을 실행합니다. 두 Lab 모두 API 키나 실제 장비 없이 로컬 Python만으로 실행할 수 있습니다.

## Lab 1. 주차장 출입 제어

```bash
python 10_labs/01_parking_gate_tool.py
```

```text
사용자 메시지 → 차량 번호 추출(Mock LLM) → 가상 DB 조회
             → 서버 출입 정책 → 일회용 승인 ID → 문 열기 Tool
```

LLM은 차량 번호를 구조화하거나 Tool을 선택할 수 있지만 출입 허가는 결정하지 않습니다. 등록 여부와 활성 권한은 서버 정책이 판단합니다. 상태를 변경하는 `open_gate`는 서버가 발급한 승인 ID가 있어야 실행되며, 승인 ID는 한 번만 사용할 수 있습니다.

확인할 사례:

- 등록되고 활성화된 `12가3456`: 문 열림
- 등록되었지만 비활성화된 `34나7890`: 문 열리지 않음
- 등록되지 않은 `99다9999`: 문 열리지 않음
- 차량 번호가 없는 메시지: 추가 정보 요청

확장 과제:

1. 승인 ID에 만료 시간을 추가합니다.
2. 입차 기록과 문을 연 시각을 별도 로그에 저장합니다.
3. 관리자의 명시적 승인이 필요한 방문 차량 절차를 추가합니다.

## Lab 2. 에어컨 자동 제어

```bash
python 10_labs/02_air_conditioner_workflow.py
```

```text
온도 센서 Tool → 규칙 판단 → 에어컨 제어 Tool → 다음 센서 값
```

- 27°C 이상이고 꺼져 있으면 켭니다.
- 23°C 이하이고 켜져 있으면 끕니다.
- 23°C 초과 27°C 미만에서는 현재 상태를 유지합니다.

켜고 끄는 기준을 다르게 두는 방식을 히스테리시스라고 합니다. 경계 온도 부근에서 에어컨이 반복해서 켜지고 꺼지는 현상을 줄입니다. 판단 규칙이 명확하므로 이 과정에는 LLM Agent가 필요하지 않습니다.

확장 과제:

1. `eco`, `comfort` 모드별 기준 온도를 추가합니다.
2. 센서 값이 허용 범위를 벗어날 때 제어를 중단하고 오류를 기록합니다.
3. 사용자의 자연어 요청은 LLM으로 구조화하되, 실제 제어는 이 Workflow가 담당하도록 결합합니다.

## Lab 3. 택배함 인증과 중복 실행 방지

```bash
python 10_labs/03_parcel_locker_authorization.py
```

인증 코드가 택배함 번호와 일치하는지, 유효 시간이 지나지 않았는지, 이미 사용되지 않았는지를 확인한 후 문을 엽니다. 정상 실행, 동일 코드의 중복 실행, 만료된 코드, 잘못된 코드, 존재하지 않는 택배함을 비교합니다.

```text
인증 코드 발급 → 택배함·만료 시각 확인 → 사용 여부 확인 → 사용 처리 + 문 열기
```

실제 서비스에서는 `사용 처리 + 문 열기 명령` 사이의 중복 요청을 막기 위해 원자적 처리나 멱등성 키를 사용해야 합니다.

## Lab 4. 카페 주문 arguments 추출

```bash
python 10_labs/04_cafe_argument_extraction.py
```

자연어 주문에서 `menu`, `size`, `quantity`를 추출합니다. 필수값이 모두 있으면 검증된 arguments를 만들고, 값이 빠졌다면 임의로 추측하지 않고 `missing_arguments`와 `follow_up_question`을 반환합니다.

확인할 사례:

- `라지 아메리카노 두 잔`: 한글 수량을 포함한 모든 arguments 추출
- `미디엄 카페라테 2 잔`: 숫자와 띄어쓰기가 있는 수량 추출
- `카페라테 주세요`: 크기와 수량 재질문
- `미디엄 한 잔 주세요`: 메뉴 재질문

예제의 추출기는 학습용 Mock입니다. 실제 연동에서는 LLM의 Tool Call arguments를 같은 Pydantic Schema로 다시 검증합니다.

## Lab 5. 도서 대출과 여러 Tool Result

```bash
python 10_labs/05_library_multi_tool_rules.py
```

회원 조회, 도서 조회, 현재 대출 목록 조회라는 세 Tool Result를 모은 뒤 서버 업무 규칙으로 대출 가능 여부를 결정합니다.

```text
회원 조회 ─┐
도서 조회 ─┼→ 대출 규칙 평가 → 대출 상태 변경 → 최종 답변
대출 조회 ─┘
```

회원 활성 상태, 연체 여부, 도서 대출 가능 상태, 최대 대출 권수를 검사합니다. LLM은 여러 결과를 설명할 수 있지만 대출 허용 여부는 백엔드 규칙이 결정해야 합니다.

## Lab 6. 재고 예약과 동시성

```bash
python 10_labs/06_inventory_reservation_concurrency.py
```

두 요청이 같은 재고와 버전을 읽은 상황을 재현합니다. 먼저 예약한 요청이 재고와 버전을 변경하면, 늦게 도착한 요청은 실행 직전에 버전을 재검증하여 `VERSION_CONFLICT`로 중단됩니다. 최신 상태로 다시 읽은 뒤에는 수량 부족도 다시 검사합니다.

```text
재고 조회(version=1) → 예약 요청
                      → 실행 직전 version·수량 재검증 → 조건부 갱신
다른 요청의 변경 ────┘
```

이 예제는 낙관적 잠금의 개념을 메모리로 단순화한 것입니다. 실제 DB에서는 트랜잭션과 `WHERE version = ?` 조건을 포함한 원자적 갱신을 사용합니다. LLM이 조금 전에 조회한 재고 수량만 믿고 예약을 확정해서는 안 됩니다.

## Provider 비교 방법

별도의 Provider 비교 Python 파일은 두지 않습니다. Mini Agent의 Streamlit `Tool 선택`과 `Agent Loop` 화면에서 같은 질문을 Gemini, GPT, Ollama/Llama에 각각 보내 다음 항목을 표로 기록합니다.

- 선택한 Tool 이름과 arguments
- 누락 정보에 대한 재질문 여부
- Tool Result를 반영한 최종 답변
- 지연 시간과 오류 처리 방식

Provider 비교는 Tool의 핵심 원리를 새로 설명하는 예제가 아니라, 이미 만든 전체 흐름을 서로 다른 모델로 관찰하는 실험입니다.
