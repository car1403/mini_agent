# 03 Tool Use 실습

기본 예제 `00`~`08`을 학습한 뒤 아래 일곱 가지 실전 Lab을 실행합니다. 모든 Lab은 API 키나 실제 장비 없이 로컬 Python만으로 실행할 수 있습니다.

## Workflow, Tool Use, AI Agent 구분

세 용어는 서로 배타적인 제품 이름이 아니라 시스템의 서로 다른 책임을 설명합니다.
`Tool Use`는 외부 기능을 호출하는 방법이고, `Workflow`와 `AI Agent`는 어떤 Tool을
언제 어떤 순서로 호출할지 결정하는 방식입니다. 따라서 Workflow도 Tool을 사용할 수
있고 Agent도 Tool을 사용할 수 있습니다.

### 1. Workflow

Workflow는 실행 단계와 분기 조건을 개발자가 미리 정의한 흐름입니다. 같은 입력과
상태에는 원칙적으로 같은 경로와 결과가 나와야 합니다.

```text
입력 → 검증 → A 실행 → 조건 확인 → B 또는 C 실행 → 종료
```

다음 상황에는 Workflow가 적합합니다.

- 단계와 순서가 사전에 정해져 있습니다.
- 승인, 인증, 결제, 출입, 재고 차감처럼 결과가 결정적이어야 합니다.
- 모든 분기를 코드와 테스트로 명확히 설명해야 합니다.
- 감사 로그, 재시도, 멱등성, Transaction이 중요합니다.
- 잘못된 판단의 비용이 크고 허용 가능한 행동 범위가 좁습니다.

Workflow에 LLM을 일부 사용할 수는 있습니다. 예를 들어 자연어에서 차량 번호나 주문
항목을 추출할 수 있지만, 추출된 값의 검증과 최종 상태 변경은 Workflow가 담당합니다.

### 2. Tool Use

Tool은 모델이나 프로그램이 외부 세계의 데이터 또는 기능을 사용하도록 만든 제한된
인터페이스입니다. 날씨 조회, 문서 검색, 재고 확인, 문 열기 등이 Tool에 해당합니다.

```text
Tool 이름 + 입력 Schema + 실행 함수 + 구조화된 결과
```

Tool Use를 적용할 때는 다음 원칙을 지킵니다.

- Tool 이름과 입력을 Schema로 정의합니다.
- LLM이 만든 arguments를 신뢰하지 않고 Backend에서 다시 검증합니다.
- 등록된 Allowlist Tool만 실행합니다.
- 조회 Tool과 상태 변경 Tool의 권한을 구분합니다.
- Timeout, 중복 실행, 실패 결과를 구조화해서 반환합니다.
- 상태 변경 Tool에는 승인 ID, 멱등성 키, Transaction 같은 추가 보호를 적용합니다.

Tool 하나를 호출했다고 Agent가 되는 것은 아닙니다. 코드가 항상 `재고 조회 → 예약`을
호출한다면 Tool을 사용하는 Workflow입니다. 현재 상태를 보고 조회할 Tool이나 종료를
동적으로 선택한다면 Tool을 사용하는 Agent입니다.

### 3. AI Agent

AI Agent는 목표와 현재 상태, 이전 Tool Result를 보고 다음 행동을 실행 시점에 선택하는
구조입니다. 다음 행동은 Tool 호출뿐 아니라 재질문, 대기, 종료일 수도 있습니다.

```text
목표·상태 확인 → 다음 행동 선택 → Tool 또는 재질문 → 결과를 상태에 반영
       ↑                                             ↓
       └──────── 종료 조건까지 제한적으로 반복 ──────┘
```

다음 상황에는 Agent가 적합합니다.

- 요청마다 필요한 정보와 Tool 호출 순서가 달라집니다.
- 자연어가 모호하여 누락 정보를 재질문해야 합니다.
- 여러 지식 저장소나 조회 Tool 중 하나를 선택해야 합니다.
- 이전 Tool Result에 따라 다음 행동이 달라집니다.
- 가능한 모든 경로를 고정 Workflow로 작성하면 분기가 지나치게 복잡해집니다.
- 최종 행동을 읽기 전용 또는 충분히 제한된 범위에 둘 수 있습니다.

Agent를 사용하더라도 무제한 자율 실행을 허용하지 않습니다. 사용할 Tool Allowlist,
최대 반복 횟수, 종료 조건, 입력 Schema, 권한과 실패 처리는 Backend가 통제합니다.

### 핵심 비교

| 기준 | Workflow | Tool Use | AI Agent |
|---|---|---|---|
| 핵심 질문 | 정해진 절차를 어떻게 실행하는가? | 외부 기능을 어떻게 안전하게 호출하는가? | 현재 상태에서 다음 행동을 무엇으로 선택하는가? |
| 실행 순서 | 개발자가 사전에 정의 | 호출 주체에 따라 다름 | 실행 중 상태와 결과에 따라 결정 |
| 판단 방식 | 명시적 조건과 규칙 | 자체 판단 방식은 없음 | LLM 또는 정책 기반 동적 선택 |
| 예측 가능성 | 높음 | 실행 함수는 높아야 함 | 상대적으로 낮으므로 제한 필요 |
| 상태 변경 | 적합, Transaction으로 보호 | 가능하지만 강한 권한 검증 필요 | 직접 맡기기보다 Backend Service에 위임 |
| 대표 사례 | 승인, 인증, 결제, 재고 차감 | 날씨·DB·검색 API 호출 | 재질문, Tool 선택, 결과 종합 |
| 필수 안전장치 | 검증, 재시도, 멱등성, Transaction | Schema, Allowlist, Timeout, 구조화 오류 | Tool 안전장치 + max steps + 종료 조건 + Trace |

### 선택 순서

새 기능을 설계할 때 다음 질문을 순서대로 확인합니다.

1. 외부 데이터 조회나 기능 실행이 필요한가?
   필요하면 Tool로 분리합니다.
2. 실행 순서와 분기 조건을 코드로 명확히 정할 수 있는가?
   그렇다면 Workflow를 우선 사용합니다.
3. 현재 상태나 Tool Result에 따라 다음 행동이 매번 달라지는가?
   그렇다면 제한된 Agent를 검토합니다.
4. 인증, 승인, 결제, 출입, 재고 변경처럼 실패 비용이 큰가?
   최종 결정과 상태 변경은 Backend Workflow가 담당합니다.
5. Agent가 꼭 필요하다면 행동 범위를 제한할 수 있는가?
   Allowlist, Schema, 권한, `max_steps`, 종료 조건과 Trace를 먼저 설계합니다.

```text
외부 기능 필요 없음 ──→ 일반 함수 또는 Service
외부 기능 필요 ───────→ Tool로 캡슐화
순서가 고정됨 ────────→ Tool을 사용하는 Workflow
순서가 동적임 ────────→ 제한된 Tool을 사용하는 Agent
중요한 상태 변경 ─────→ Agent 제안 + Backend Workflow 최종 결정
```

### Agent를 사용하지 말아야 하는 경우

- 단순한 `if/else` 규칙으로 충분한 경우
- 법적·금전적 승인 결과를 LLM 판단 하나로 결정하는 경우
- DB Transaction이나 동시성 제어가 필요한 경우
- Tool 입력과 실행 범위를 검증할 수 없는 경우
- 종료 조건이나 최대 실행 횟수를 정의할 수 없는 경우
- 같은 입력에 항상 같은 결과가 필요한 경우

실무에서는 Workflow와 Agent를 결합하는 경우가 많습니다. Agent는 사용자 의도 파악,
누락 정보 재질문, 읽기 전용 Tool 선택과 결과 요약을 담당하고, Workflow는 인증·승인,
업무 규칙 검증과 상태 변경을 담당합니다.

## Lab 구성 원칙

| Lab | 현재 성격 | Agent 여부 | 학습 방향 |
|---:|---|---|---|
| 01 주차장 출입 | Tool + 승인 Workflow | 아니오 | 안전한 상태 변경 Workflow로 유지 |
| 02 에어컨 제어 | 규칙 기반 Workflow | 아니오 | Agent가 필요 없는 반례로 유지 |
| 03 택배함 인증 | 인증·멱등성 Workflow | 아니오 | 백엔드 보안 정책으로 유지 |
| 04 카페 주문 | arguments 추출 + 재질문 | 부분적 Agent | 상태를 유지하는 단일 Agent Cycle |
| 05 도서 대출 | 동적 조회 Tool 선택 | 학습용 Agent | 제한된 반복 Agent Loop와 서버 정책 분리 |
| 06 재고 예약 | 동시성·낙관적 잠금 | 아니오 | 안전한 Tool 실행 정책으로 유지 |
| 07 여행 준비 | 재질문 + Multi-Tool + 결과 종합 | 예 | 읽기 전용 Agent의 판단과 종료 조건 학습 |

여러 Tool을 사용한다고 모두 Agent인 것은 아닙니다. 정해진 순서대로 실행하면
Workflow이고, 현재 상태에 따라 다음 Tool·재질문·종료를 선택하면 Agent입니다.
반대로 승인, 인증, 동시성처럼 결과가 결정적이어야 하는 정책은 Agent가 아니라
Backend Service가 담당해야 합니다.

## Lab 1. 주차장 출입 제어

```bash
python 10_labs/01_parking_gate_tool.py
```

```text
사용자 메시지 → 차량 번호 추출(Mock LLM) → 가상 DB 조회
             → 서버 출입 정책 → 일회용 승인 ID → 문 열기 Tool
```

LLM은 차량 번호를 구조화하거나 Tool을 선택할 수 있지만 출입 허가는 결정하지 않습니다. 등록 여부와 활성 권한은 서버 정책이 판단합니다. 상태를 변경하는 `open_gate`는 서버가 발급한 승인 ID가 있어야 실행되며, 승인 ID는 한 번만 사용할 수 있습니다.

### 왜 Tool + 승인 Workflow인가?

- 차량 조회와 문 열기는 외부 기능이므로 Tool로 분리합니다.
- 조회 → 권한 검증 → 승인 ID 발급 → 문 열기 순서는 고정되어 있어 Workflow가 적합합니다.
- 출입 허가는 보안 상태 변경이므로 확률적인 Agent 판단에 맡기지 않습니다.
- Agent를 추가하더라도 차량 번호 추출이나 누락 정보 재질문까지만 담당해야 합니다.

확인할 사례:

- 등록되고 활성화된 `12가3456`: 문 열림
- 등록되었지만 비활성화된 `34나7890`: 문 열리지 않음
- 등록되지 않은 `99다9999`: 문 열리지 않음
- 차량 번호가 없는 메시지: 추가 정보 요청

확장 과제:

1. 승인 ID에 만료 시간을 추가합니다.
2. 입차 기록과 문을 연 시각을 별도 로그에 저장합니다.
3. 관리자의 명시적 승인이 필요한 방문 차량 절차를 추가합니다.

## Lab 2. 에어컨 자동 제어

```bash
python 10_labs/02_air_conditioner_workflow.py
```

```text
온도 센서 Tool → 규칙 판단 → 에어컨 제어 Tool → 다음 센서 값
```

- 27°C 이상이고 꺼져 있으면 켭니다.
- 23°C 이하이고 켜져 있으면 끕니다.
- 23°C 초과 27°C 미만에서는 현재 상태를 유지합니다.

켜고 끄는 기준을 다르게 두는 방식을 히스테리시스라고 합니다. 경계 온도 부근에서 에어컨이 반복해서 켜지고 꺼지는 현상을 줄입니다. 판단 규칙이 명확하므로 이 과정에는 LLM Agent가 필요하지 않습니다.

### 왜 규칙 기반 Workflow인가?

- 센서 조회와 장치 제어는 Tool이지만 제어 기준과 호출 순서가 완전히 정해져 있습니다.
- 동일한 온도와 현재 상태에는 동일한 제어 결과가 필요합니다.
- LLM Agent를 사용하면 비용과 지연이 늘고 동일 조건에서 판단이 달라질 위험이 있습니다.
- 자연어 설정이 필요할 때만 LLM으로 희망 모드를 구조화하고 실제 제어는 Workflow가 수행합니다.

확장 과제:

1. `eco`, `comfort` 모드별 기준 온도를 추가합니다.
2. 센서 값이 허용 범위를 벗어날 때 제어를 중단하고 오류를 기록합니다.
3. 사용자의 자연어 요청은 LLM으로 구조화하되, 실제 제어는 이 Workflow가 담당하도록 결합합니다.

## Lab 3. 택배함 인증과 중복 실행 방지

```bash
python 10_labs/03_parcel_locker_authorization.py
```

인증 코드가 택배함 번호와 일치하는지, 유효 시간이 지나지 않았는지, 이미 사용되지 않았는지를 확인한 후 문을 엽니다. 정상 실행, 동일 코드의 중복 실행, 만료된 코드, 잘못된 코드, 존재하지 않는 택배함을 비교합니다.

```text
인증 코드 발급 → 택배함·만료 시각 확인 → 사용 여부 확인 → 사용 처리 + 문 열기
```

실제 서비스에서는 `사용 처리 + 문 열기 명령` 사이의 중복 요청을 막기 위해 원자적 처리나 멱등성 키를 사용해야 합니다.

### 왜 인증·멱등성 Workflow인가?

- 코드 유효성, 만료와 사용 여부는 명시적인 참·거짓 규칙입니다.
- 같은 인증 코드로 문이 두 번 열리지 않도록 원자적 상태 변경이 필요합니다.
- Agent가 이전 조회 결과만 믿고 문을 열면 만료나 동시 요청을 놓칠 수 있습니다.
- Agent는 택배함 번호나 인증 코드가 누락됐을 때 재질문하는 역할까지만 맡을 수 있습니다.

## Lab 4. 카페 주문 arguments 추출

```bash
python 10_labs/04_cafe_argument_extraction.py
```

자연어 주문에서 `menu`, `size`, `quantity`를 추출합니다. 한 번의 사용자 메시지마다
단일 Agent Cycle을 실행하고, 이전에 수집한 arguments를 상태에 보존합니다. 필수값이
빠졌다면 임의로 추측하지 않고 재질문하며 다음 입력에서 기존 값과 새 값을 병합합니다.

확인할 사례:

- `라지 아메리카노 두 잔`: 한글 수량을 포함한 모든 arguments 추출
- `미디엄 카페라테 2 잔`: 숫자와 띄어쓰기가 있는 수량 추출
- `카페라테 주세요`: 크기와 수량 재질문
- `미디엄 한 잔 주세요`: 메뉴 재질문

예제의 추출기는 학습용 Mock입니다. 실제 연동에서는 LLM의 Tool Call arguments를 같은 Pydantic Schema로 다시 검증합니다.

### 왜 부분적 Agent인가?

- 사용자는 메뉴, 크기와 수량을 한 번에 말하지 않을 수 있어 재질문 선택이 필요합니다.
- 이전 대화에서 수집한 값과 새 입력을 병합하는 상태가 필요합니다.
- 주문 정보가 완성되면 종료한다는 명확한 종료 조건이 있습니다.
- 결제나 주문 확정까지 Agent에 맡기지 않고, 구조화·재질문 단계만 Agent로 구성합니다.

## Lab 5. 도서 대출과 동적 Tool 선택 Agent

```bash
python 10_labs/05_library_multi_tool_rules.py
```

Agent가 현재 상태에서 부족한 정보를 확인해 회원 조회, 도서 조회, 현재 대출 목록
조회 중 다음 Tool을 선택합니다. 필요한 근거가 모두 모이면 종료를 선택하고, 서버
업무 규칙이 대출 가능 여부와 실제 상태 변경을 결정합니다.

```text
Agent 상태 확인 → 다음 조회 Tool 선택 → Tool Result를 상태에 저장
       ↑                                      ↓
       └──────── 근거가 부족하면 반복 ────────┘
근거가 충분하면 종료 선택 → 서버 대출 규칙 → 상태 변경 → 최종 결과
```

최대 반복 횟수와 종료 이유를 Trace로 확인할 수 있습니다. 실제 LLM Provider로 교체해도
대출 허용 여부는 반드시 백엔드 규칙이 결정해야 합니다.

### 왜 동적 Tool 선택 Agent + Backend Workflow인가?

- 회원, 도서, 대출 목록 중 어떤 정보가 부족한지는 현재 상태에 따라 달라집니다.
- 필요한 조회 Tool의 순서를 모든 경우에 고정하면 불필요한 호출이 발생합니다.
- 따라서 Agent가 다음 조회 Tool 또는 종료를 선택합니다.
- 대출 한도, 회원 상태와 실제 대출 처리는 결정적 업무 규칙이므로 Backend가 담당합니다.
- 이 구조는 `Agent가 근거 수집 → Workflow가 최종 결정`하는 대표적인 혼합 패턴입니다.

## Lab 6. 재고 예약과 동시성

```bash
python 10_labs/06_inventory_reservation_concurrency.py
```

두 요청이 같은 재고와 버전을 읽은 상황을 재현합니다. 먼저 예약한 요청이 재고와 버전을 변경하면, 늦게 도착한 요청은 실행 직전에 버전을 재검증하여 `VERSION_CONFLICT`로 중단됩니다. 최신 상태로 다시 읽은 뒤에는 수량 부족도 다시 검사합니다.

```text
재고 조회(version=1) → 예약 요청
                      → 실행 직전 version·수량 재검증 → 조건부 갱신
다른 요청의 변경 ────┘
```

이 예제는 낙관적 잠금의 개념을 메모리로 단순화한 것입니다. 실제 DB에서는 트랜잭션과 `WHERE version = ?` 조건을 포함한 원자적 갱신을 사용합니다. LLM이 조금 전에 조회한 재고 수량만 믿고 예약을 확정해서는 안 됩니다.

### 왜 동시성 Workflow인가?

- 예약 성공은 실행 시점의 최신 재고와 Version으로 결정해야 합니다.
- 조회 이후 다른 요청이 재고를 변경할 수 있으므로 이전 Tool Result만으로 확정할 수 없습니다.
- 조건부 갱신과 Transaction은 DB와 Backend가 보장해야 하는 기술적 불변 조건입니다.
- Agent는 상품 탐색이나 대안 제안은 할 수 있지만 재고 차감 성공 여부는 결정하지 않습니다.

## Lab 7. 여행 준비 Multi-Tool Agent

```bash
python 10_labs/07_travel_planning_agent.py
```

도시나 날짜가 빠지면 재질문하고, 오늘 여행에는 현재 날씨 Tool을, 미래 여행에는
예보 Tool을 선택합니다. 날씨 결과를 얻은 뒤 관광지 Tool을 추가로 호출하고 충분한
근거가 모이면 여행 준비 정보를 조립하여 종료합니다.

```text
사용자 요청 → 도시·날짜 확인 ── 부족함 → 재질문 후 상태 유지
                         └─ 충분함 → 현재 날씨 또는 미래 예보
                                      → 관광지 검색 → 결과 종합 → 종료
```

확인할 항목:

1. 첫 번째 Cycle에서 누락된 도시만 재질문하는지 확인합니다.
2. 두 번째 Cycle에서 이전 날짜와 새 도시가 병합되는지 확인합니다.
3. Agent가 현재 날씨와 미래 예보 중 하나만 선택하는지 확인합니다.
4. `max_steps`, `termination_reason`, 전체 Trace를 확인합니다.
5. 미등록 Tool과 잘못된 arguments가 Backend Executor에서 차단되는지 확인합니다.

### 왜 Multi-Tool Agent인가?

- 도시와 날짜가 빠졌는지에 따라 재질문 여부가 달라집니다.
- 오늘과 미래 날짜에 따라 현재 날씨 또는 예보 Tool 중 하나를 선택해야 합니다.
- 날씨 결과를 받은 뒤 관광지 검색으로 진행하는 등 이전 결과가 다음 행동에 영향을 줍니다.
- 조회 전용 Tool만 허용하고 `max_steps`와 종료 조건을 두어 Agent의 행동 범위를 제한할 수 있습니다.
- 예약이나 결제 같은 상태 변경이 없어 Agent의 동적 판단을 학습하기에 안전한 사례입니다.

## Provider 비교 방법

별도의 Provider 비교 Python 파일은 두지 않습니다. Mini Agent의 Streamlit `Tool 선택`과 `Agent Cycle` 화면에서 같은 질문을 Gemini, GPT, Ollama/Llama에 각각 보내 다음 항목을 표로 기록합니다.

- 선택한 Tool 이름과 arguments
- 누락 정보에 대한 재질문 여부
- Tool Result를 반영한 최종 답변
- 지연 시간과 오류 처리 방식

Provider 비교는 Tool의 핵심 원리를 새로 설명하는 예제가 아니라, 이미 만든 전체 흐름을 서로 다른 모델로 관찰하는 실험입니다.
